# L 组数据报表 · 取值规则说明

> 位置：`http://web.sms62.com/mkt/port` 页面，筛选条件与列表之间的「📊 L 组数据报表」可折叠面板
> 适用脚本：`sms62-port-lbuttons.user.js` v1.10.3+

---

## 一、数据来源

| 项目 | 说明 |
|---|---|
| 明细数据 | `GET /prod-api/business/port/list`，`pageSize=1000` 并行分页拉**全量** |
| 状态名称 | `GET /prod-api/system/dict/data/type/sys_port_status`（本地缓存 1 天） |
| 设备分组 | 业务配置 `LOCATION:DEVICES:CONFIG`（如 `{"L1":"D1,D2,D3", ...}`） |

**关键点：报表统计的是「全部端口数据」，与页面当前的筛选条件、页码、每页条数完全无关。** 你在列表上筛了设备/状态，报表数字不会跟着变。

### 数据刷新时机

| 场景 | 行为 |
|---|---|
| 打开页面 | 先渲染 sessionStorage 缓存（秒开），数据超过 30 秒则后台静默拉最新并原地替换 |
| 停留页面 | 每 60 秒静默保鲜一次；切回标签页立即补一次 |
| 站点发生写操作（推送、改状态等） | 标记失效，下次刷新强制走网络 |
| 点「刷新报表」 | 强制绕过缓存拉最新 |
| 改阈值输入框 | 只用已拉到的数据重算，**不发请求** |

## 二、分组归属规则（哪些端口算进某个 L 组）

以端口记录的**设备名**（`deviceName`）与配置里的设备编号比对，命中任一即归入该组：

1. **完全相同** → 命中。`D1` = `D1`
2. 设备名含分隔符（空格 `/` `|` `,` `，` `、` `()` `（）` `[]` `【】` `-`）时，**切分后某一段完全相同** → 命中。如 `D1 / 移动`、`D1-移动` 都会归入含 `D1` 的组

一台设备只应出现在一个组里（配置本身不重叠的前提下），因此各组互不重复计数。

## 三、各列取值规则

| 列 | 含义 | 取值规则 |
|---|---|---|
| **分组** | 组名 + 设备清单 | 组名来自配置 key（L1~L5/N）；括号内灰色小字是该组设备编号，来自配置值 |
| **端口总数** | 该组的端口记录条数 | 该组名下匹配到的行数（`count`），不是卡号去重数 |
| **套餐总数** | 该组套餐额度合计 | 组内所有行 `pkgs` **数值求和**；空/null 按 0 计。注意这是「额度相加」，不是「有套餐的卡数」 |
| **套餐＜N** | 套餐不足的端口数 | 组内 `pkgs` **有值**且 **小于 N** 的行数（`count`）。空/null/非数字**不计入**。N 默认 1000，可在面板头部输入框修改 |
| **发不出去** | 疑似已废的卡数 | 见下方专节，三条件同时满足才计数 |
| **状态分布** | 各状态的端口数 | 组内按状态名分组计数，**按数量降序**排列为彩色标签；状态值不在字典里显示为原始值或「未知」 |

### 阈值 N（套餐＜N）

- 位置：面板头部「套餐＜ [1000]」，改完失焦或回车即重算
- 默认 `1000`；实际值存入 `sessionStorage`，**刷新页面保留**，关闭标签页恢复默认
- **「换卡推送」批量流程的勾选条件同步使用这个 N**（点批量那一刻取一次快照，运行中改输入框不影响本轮）

## 四、「发不出去」判定（重点）

三条件**全部满足**才计入：

| # | 条件 | 字段 |
|---|---|---|
| 1 | 状态名包含「**封卡**」（疑被封卡、疑似封卡等均命中） | `status` 经字典翻译后的标签 |
| 2 | **充值次数 ≥ 1** | `topupCount` |
| 3 | **失败数量 ≥ 有效发送数**，且有效发送数 > 0 | `recentSendFailCount` vs 下方公式 |

### 有效发送数公式

```
若 充值次数 > 1：有效发送数 = 发送总数 − (充值次数 − 1) × 1500
若 充值次数 = 1：有效发送数 = 发送总数（不扣减）
```

> 解释：每次充值带来 1500 条发送额度。充值 N 次意味着历史上已用掉 (N−1)×1500 的旧额度，只有扣除这部分后剩余的发送量，才是「本次充值周期内真正发出去的条数」。失败数量达到这个数，说明这一轮基本没发出去。

### 示例

| 状态 | 发送总数 | 充值次数 | 失败数量 | 有效发送数 | 是否计入 |
|---|---|---|---|---|---|
| 疑被封卡 | 800 | 1 | 800 | 800 | ✅ |
| 疑被封卡 | 800 | 1 | 799 | 800 | ❌（差 1 条） |
| 疑被封卡 | 3200 | 2 | 1700 | 3200−1500=1700 | ✅ |
| 疑被封卡 | 4600 | 3 | 1600 | 4600−3000=1600 | ✅ |
| 疑被封卡 | 4600 | 3 | 1599 | 1600 | ❌ |
| 疑被封卡 | 1500 | 2 | 0 | 0（≤0 不算） | ❌ |
| 在线 | 800 | 1 | 800 | 800 | ❌（状态非封卡） |
| 疑被封卡 | 300 | 0 | 300 | — | ❌（充值 0 次） |

> 严格讲 `> 1` 与 `≥ 2` 等价；当前代码常量 `CANT_SEND_MIN_TOPUP = 1`（含 1），扣减仅在 `topupCount > 1` 时生效。

## 五、汇总行

表格最后一行为「汇总」（浅灰底、加粗）：

- **端口总数 / 套餐总数 / 套餐＜N / 发不出去** → 各组合并求和
- **状态分布** → 跨组同名状态合并计数，按总数降序

## 六、交互

| 点击对象 | 效果 |
|---|---|
| 分组行的状态标签 | 「设备」筛选设为该组设备 + 「状态」设为该状态 → 自动查询（结果 = 该组该状态的端口） |
| 汇总行的状态标签 | **清空**「设备」筛选 + 「状态」设为该状态 → 自动查询（结果 = 全部设备中该状态的端口） |
| 「刷新报表」 | 强制绕过缓存拉最新数据 |
| 面板头部折叠条 | 收起/展开面板 |

筛选后列表条数应与所点标签的数字一致；若不一致，先确认是否还有其他残留筛选条件（如运营商、卡号）。

## 七、常见疑问

**Q：报表数字和页面列表总数对不上？**
A：报表统计全量数据，列表受当前筛选/分页影响。点「刷新报表」或清空筛选后再比。

**Q：「套餐总数」是什么单位？**
A：是 `pkgs` 字段的数值求和（额度累加），不是卡数量。要看卡数量看「端口总数」。

**Q：「发不出去」是 0，但明明有封卡的？**
A：打开浏览器控制台（F12）搜 `[L按钮]`，会打印「封卡 N 张，其中充值次数≥1 的 M 张」，据此判断是状态名没匹配、充值次数不足、还是失败数没到有效发送数。

**Q：为什么改了阈值，批量推送用的值也变了？**
A：两者故意联动，保证「报表看到的套餐＜N」和「批量勾选的套餐＜N」口径一致。批量开始时会在进度浮层与日志中打印本次实际使用的阈值。

**Q：单台设备端口超过 1000 条会漏统计吗？**
A：报表不会（分页拉全量）；但「换卡推送」批量是勾选**当前页**的行，超过每页条数时控制台会告警「超出部分未参与勾选」。
